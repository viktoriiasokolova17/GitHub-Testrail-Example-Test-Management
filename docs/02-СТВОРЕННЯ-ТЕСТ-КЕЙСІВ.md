# 📝 Створення тест-кейсів

Як створювати та організовувати тест-кейси.

---

## Способи створення тест-кейсів

### Спосіб 1: Через GitHub Issues (рекомендовано)

**Переваги:**
- Зручна форма з валідацією
- Автоматичні мітки
- Відстеження історії
- Коментарі та обговорення

**Як створити:**

1. Відкрийте репозиторій на GitHub
2. **Issues** → **New Issue**
3. Виберіть **"🧪 Тест-кейс"**
4. Заповніть форму:
   - **ID тест-кейсу**: `TC-AUTH-001`
   - **Тестовий набір**: `Автентифікація`
   - **Пріоритет**: `🔴 Критичний`
   - **Тип тесту**: `Функціональний`
   - **Передумови**: що потрібно перед тестом
   - **Кроки тестування**: покрокова інструкція
   - **Очікуваний результат**: що повинно статися
5. Натисніть **Submit new issue**

### Спосіб 2: Через Markdown файли

**Переваги:**
- Контроль версій через Git
- Робота офлайн
- Bulk редагування

**Структура файлу:**

```markdown
# TC-XXX-000: Назва тест-кейсу

## Метадані

| Поле | Значення |
|------|----------|
| **ID** | TC-XXX-000 |
| **Набір** | Назва набору |
| **Секція** | Назва секції |
| **Пріоритет** | 🔴 Критичний / 🟠 Високий / 🟡 Середній / 🟢 Низький |
| **Тип** | Функціональний / Регресійний / Димовий |
| **Автоматизація** | Ручний / Автоматизовано / Планується |
| **Створено** | YYYY-MM-DD |
| **Автор** | @username |

## Передумови

- Передумова 1
- Передумова 2

## Кроки тестування

| Крок | Дія | Очікуваний результат |
|------|-----|---------------------|
| 1 | Опис дії | Очікуваний результат |
| 2 | Опис дії | Очікуваний результат |

## Тестові дані

\```
Ключ: Значення
\```

## Примітки

Додаткові примітки.

## Історія виконання

| Дата | ID прогону | Тестувальник | Статус | Примітки |
|------|------------|--------------|--------|----------|
| | | | | |
```

## Угоди про найменування

### ID тест-кейсів

Формат: `TC-{НАБІР}-{НОМЕР}`

- `TC` - Test Case (тест-кейс)
- `{НАБІР}` - короткий ідентифікатор набору (AUTH, PAY, USER, API)
- `{НОМЕР}` - трицифровий порядковий номер

**Приклади:**
- `TC-AUTH-001` - перший тест автентифікації
- `TC-PAY-015` - 15-й тест платежів
- `TC-API-100` - 100-й API тест

### Структура папок

```
test-cases/
├── auth/                    # Автентифікація
│   ├── login/              # Вхід
│   │   ├── TC-AUTH-001.md
│   │   └── TC-AUTH-002.md
│   └── logout/             # Вихід
│       └── TC-AUTH-010.md
├── payments/               # Платежі
│   ├── checkout/
│   └── refunds/
└── users/                  # Користувачі
    ├── profile/
    └── settings/
```

## Пріоритети

| Пріоритет | Опис | Приклади |
|-----------|------|----------|
| 🔴 Критичний | Блокує реліз, основний функціонал | Логін, оплата, реєстрація |
| 🟠 Високий | Важливий функціонал | Редагування профілю, фільтри |
| 🟡 Середній | Стандартна важливість | Налаштування, допоміжні функції |
| 🟢 Низький | Незначний, nice-to-have | Косметичні, edge cases |

---

## Типи тестів

| Тип | Опис | Коли використовувати |
|-----|------|---------------------|
| **Димовий (Smoke)** | Базова перевірка працездатності | Після кожного деплою |
| **Функціональний** | Перевірка конкретної функції | Нові фічі, баг-фікси |
| **Регресійний** | Перевірка існуючого функціоналу | Перед релізом |
| **E2E** | Повний шлях користувача | Критичні сценарії |
| **Інтеграційний** | Взаємодія компонентів | API, сервіси |
| **Продуктивність** | Швидкість, навантаження | Оптимізація |
| **Безпека** | Уразливості, захист | Авторизація, дані |

## Найкращі практики

### ✅ Рекомендовано

1. **Один тест = одна перевірка**
   - ❌ "Перевірити логін, реєстрацію та відновлення паролю"
   - ✅ "Перевірити логін з валідними даними"

2. **Конкретні кроки**
   - ❌ "Заповнити форму"
   - ✅ "Ввести email 'test@example.com' у поле 'Email'"

3. **Вимірювані очікування**
   - ❌ "Сторінка повинна завантажитись швидко"
   - ✅ "Сторінка завантажується за < 3 секунди"

4. **Незалежність тестів**
   - Кожен тест можна виконати окремо
   - Не залежить від результатів інших тестів

5. **Актуальність**
   - Оновлюйте тести при зміні функціоналу
   - Видаляйте застарілі тести

### ❌ Уникайте

1. **Залежних тестів** - кожен тест незалежний
2. **Хардкоду** - використовуйте змінні для даних
3. **Надто довгих тестів** - розбивайте на менші
4. **Неточних кроків** - будьте конкретними
5. **Відсутніх передумов** - завжди вказуйте контекст

## Приклади хороших тест-кейсів

### Приклад 1: Функціональний тест

```markdown
# TC-AUTH-001: Вхід з валідними даними

## Передумови
- Користувач зареєстрований в системі
- Користувач не авторизований
- Cookies очищено

## Кроки тестування

| Крок | Дія | Очікуваний результат |
|------|-----|---------------------|
| 1 | Відкрити /login | Сторінка входу завантажена |
| 2 | Ввести email: test@example.com | Email прийнято |
| 3 | Ввести пароль: Password123! | Пароль замаскований |
| 4 | Натиснути "Увійти" | Індикатор завантаження |
| 5 | Дочекатися відповіді | Редирект на /dashboard |
| 6 | Перевірити header | Відображається ім'я користувача |

## Тестові дані
Email: test@example.com
Пароль: Password123!
```

### Приклад 2: Негативний тест

```markdown
# TC-AUTH-002: Вхід з невірним паролем

## Передумови
- Користувач зареєстрований в системі

## Кроки тестування

| Крок | Дія | Очікуваний результат |
|------|-----|---------------------|
| 1 | Відкрити /login | Сторінка завантажена |
| 2 | Ввести валідний email | Email прийнято |
| 3 | Ввести невірний пароль | Пароль прийнято |
| 4 | Натиснути "Увійти" | Помилка авторизації |
| 5 | Перевірити повідомлення | "Невірний email або пароль" |
| 6 | Перевірити URL | Залишається /login |

## Примітки
- Повідомлення НЕ повинно розкривати, чи існує email
- Поле паролю очищується після невдачі
```
